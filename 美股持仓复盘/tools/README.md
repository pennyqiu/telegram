# tools

两件事：**把持仓从 IB 拉下来**（省掉手抄截图），以及**每天把规则里的时限和今天的日期比对一遍**
（省掉「写完就忘」）。

## 文件

| 文件 | 作用 |
|------|------|
| `generate_snapshot.py` | 只读连接 IB，拉账户与持仓，算好穿透暴露与期权名义敞口，输出快照 |
| `etf_weights.json` | ETF 穿透计算用的指数权重表，需要定期更新 |
| `risk_calc.py` | 期权压力测试与额度倒推 |
| `check_discipline.py` | **组合纪律检查**：逾期决策、21 DTE 闸门、台账过期、复盘节奏。见下方专节 |
| `test_check_discipline.py` | 上一项的自检，无第三方依赖 |
| `daily_discipline_cron.sh` | 纪律检查的每日 cron 入口 |
| `build_site.py` | 打包全部 Markdown 成单页站点 |

## 依赖

需要 **Python 3.10 或更高版本**（`ib_async` 的要求）。本机系统 Python 是 3.9，
请用 pyenv、conda 或 Homebrew 装一个新版本，或者复用 `../../ib_monitor/` 的 Docker 环境。

```bash
pip install ib_async
```

## 使用

先确认 IB Gateway 或 TWS 已登录，且 API 端口开着。
**强烈建议在 Gateway → Configure → API → Settings 里勾选 Read-Only API**，
这样即使脚本有问题，Gateway 也会在连接层拒绝任何下单请求。

```bash
export IB_HOST=127.0.0.1
export IB_PORT=4001          # Gateway 实盘 4001 / 模拟 4002；TWS 是 7496 / 7497
export IB_CLIENT_ID=20       # 不要和 ib_monitor(10)、ib_quant 撞号

python generate_snapshot.py              # 拉全部账户，写入 ../历史复盘/持仓快照-<今天>.md
python generate_snapshot.py --stdout     # 打印到终端，先看看再决定
python generate_snapshot.py --account U1234567 --account U7654321   # 只拉指定账户
```

**默认拉取该连接下的全部账户**，这正是复盘体系要求的合并口径。
只有在明确想看单个账户时才用 `--account`。

文件已存在时脚本会拒绝覆盖，避免误删已经手工填过的快照。

## 脚本算什么、不算什么

**自动算好的**：

- 各账户与合并的净值、股票市值、期权市值、现金
- 逐笔持仓的市值、占比、浮动盈亏
- ETF 穿透后的单标的暴露与行业暴露
- 每张 Put 的名义金额、名义总额、现金覆盖率
- 到期日集中度（超过净值 10% 会标 ⚠️）
- 追高检查表中同时持有正股的标的的「距现价」

**必须手填的**：

- 「我的一句话投资逻辑」——这是刻意留白，不能自动化。它是下次判断逻辑是否走坏的唯一基准，
  让机器代写就失去了全部意义
- 每张期权的「意图」（接货型 / 收租型）——只有你知道，而这决定了适用哪套额度规则
- 52 周高点——脚本无法可靠获取，请从券商或行情网站核对后填入
- 规则卡合规自检表、心态记录、大额支出计划

## 关于 etf_weights.json

指数权重逐日变动，这份表是**估算**，用于穿透计算时精度约 ±0.5 个百分点（单标的）
和 ±2 个百分点（行业）。建议每季度深度复盘时更新一次，更新后改一下 `_updated` 字段。

数据来源：

- 纳斯达克100 权重：ETF 发行商公布的持仓明细（iShares、Invesco 官网或 etfdb）
- 标普500 权重：slickcharts 或 iShares IVV 的 latest-holdings.csv
- 主题 ETF：发行商 factsheet

`sectors` 里的行业比例各 ETF 之和不等于 1，剩余部分是可选消费、工业、金融等未单独跟踪的行业，
所以行业表的合计会小于净值——这是预期行为，不是 bug。

`direct_sectors` 用于给直接持有的个股归类。**新增个股持仓后记得在这里补一行**，
否则它不会出现在行业穿透表里。

## check_discipline.py · 组合纪律检查

### 它解决什么

[决策日志](../决策日志.md) 第 118 行给这套体系下过一个诊断：

> 纪律条文本身写得很好，缺的是**定期把条文和当前数字放在一起比对的动作**。

第 134 行的结论是「**首要矛盾是执行率，不是认知准确率**」。这个脚本就是那个缺失的动作，
每天自动做一遍。它不产生任何新判断，只回答一个问题：**你自己写下的时限，今天有哪些到了。**

### 检查什么

只做**不需要行情**的那一层，因此没有数据源可以静默失效：

| 检查 | 依据 | 数据来源 |
|------|------|----------|
| 决策逾期与临期 | 各条的失效期限 | 决策日志 §一 |
| 期权 21 DTE 时间闸门 | 规则 A3、T5 | 决策日志 §B 的到期日反推 |
| 台账过期 | 到期日已过却还挂着 | 决策日志 §B |
| 复盘节奏 | README 的月度 / 季度四层设计 | `历史复盘/持仓快照-*.md` 的最新日期 |
| 财报日（可选，需网络） | 财报后要核对标的档案第三节 | `api.tgfootclub.com/api/calendar` |

**规则原文不在脚本里抄写**，运行时从 [投资规则卡](../投资规则卡.md) 解析。规则卡改了措辞
这边自动跟上，不会出现「知识在仓库里，但没有传导到配置」那种漂移——这正是 SPLG 改名
十个月没被发现的成因。

### 用法

```bash
python3 check_discipline.py                    # 打印报告
python3 check_discipline.py --json             # 机器可读
python3 check_discipline.py --email            # 发邮件
python3 check_discipline.py --today 2026-09-20 # 指定日期，看未来某天会报什么
python3 check_discipline.py --earnings         # 额外查财报日（需要网络）

python3 test_check_discipline.py               # 自检
```

`--due-soon N` 调决策临期的提前量（默认 7 天），`--gate-lead N` 调闸门提前量（默认 7 天）。

### 邮件

SMTP 复用 `friends/tools/qdii_email.env`；**收件人不复用**那份名单。
本报告含持仓、期权义务与现金缺口，而 `qdii_email_recipients.txt` 里有朋友。
收件人写在 `discipline_recipients.txt`（已 gitignore，模板见 `.example.txt`），
或用环境变量 `DISCIPLINE_RECIPIENTS`。代码里没有回退到朋友名单的路径，这是刻意的。

默认**每次都发**，包括全部合规的日子——收件人只有自己，心跳的价值高于噪音。
不想收干净日的信就加 `--email-only-alerts`。

### 两个刻意的设计

**一、以决策日志的状态列为准，不猜。** 已经处理但没更新状态的条目会一直被报出来。
这不是 bug：它让「台账不更新」的成本立刻显现，而不是攒到下次复盘才发现对不上。
处理完请顺手把状态改掉。

**二、解析不了就大声报错。** 表格结构变了、到期日写成「待定」，脚本会把标题写成
「解析失败」并以非零码退出，而不是安静地少检查几行然后输出「全部合规」。
`friends/tools/README.md` §5.6 记过这个教训：停更的行情不会报错，它会给出一个看着很正常的数字。

### 已知边界

- 只看**日期**，不看价格与仓位。价格越线（各标的档案的买入区间、加仓动手价、减仓触发价）
  和集中度越线（P1–P7）需要行情与合并持仓，属于后续的层，其中集中度还卡在 D007。
- 期权数据来自决策日志 §B 这张手工表，不是从 IB 实时拉的。表不更新，闸门就算错。
  想要实时口径，得先让 `generate_snapshot.py` 定期跑起来。
- 财报日那一项依赖外部 API，失败时会在报告里显式写明失败了几只，不会假装查过。

## 只读保证

- 连接时 `readonly=True`
- 代码不 import 任何 Order 相关类，物理上无法下单
- 期权行情用「短暂订阅 → 取到价格 → 立即 cancelMktData」的方式，不长期占用 IB 的市场数据行

## 已知限制

- 盘后运行时期权可能取不到价格，脚本会在日志里列出哪些头寸需要手工补
- 只处理 STK 和 OPT 两类，其他品种（期货、外汇）不在支持范围
- 名义金额只对**卖出的 Put** 计算，Covered Call 的敞口是股票本身，不重复计
